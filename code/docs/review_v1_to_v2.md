## 2. v1에서 발견된 기술적 문제점

### 심각 (v2에서 반드시 수정)

| # | 문제 | 영향 | v2 해결 |
|---|---|---|---|
| 1 | **pygame + asyncio 충돌** | pygame.mixer가 asyncio 루프를 블로킹 → YOLO 감지 멈춤, WebSocket 지연 | Audio Thread 분리 |
| 2 | **LLM 동기 호출이 이벤트 루프 차단** | LLM 응답 대기 2~5초 동안 전체 시스템 정지 | asyncio.to_thread() |
| 3 | **TTS 임시 파일 누적** | tempfile(delete=False) 후 정리 없음 → 테스트 시 디스크 누적 | 세션 기반 캐시 + 대시보드 삭제 |
| 4 | **requirements.txt 비어있음** | 실제 파일에 패키지 목록 없음 → 환경 재현 불가 | 실제 패키지 기입 |
| 5 | **디렉토리 구조 미생성** | ai_core/, server/ 등 폴더 없음 → import 불가 | Step 0-3으로 앞당김 |

### 중간 (v2에서 개선)

| # | 문제 | 영향 | v2 해결 |
|---|---|---|---|
| 6 | **긴급 알림이 모든 Stage에서 활성** | Stage 1(대화만)에서도 초음파 경고 발생 가능 | Stage 3 전용으로 제한 |
| 7 | **Detection loop FPS 무제한** | YOLO가 빠르면 CPU 100% | 30fps 제한 (asyncio.sleep(0.033)) |
| 8 | **config.py 검증 없음** | API 키 누락 시 런타임 에러 → 디버깅 시간 낭비 | fail-fast 검증 |
| 9 | **.gitignore 불완전** | *.pt, audio/fallback/*.mp3 누락 → 대용량 파일 push 위험 | 패턴 추가 |

### 경미 (인지하고 진행)

| # | 문제 | 설명 |
|---|---|---|
| 10 | 순환 import 위험 | main.py ↔ server 모듈 간 상호 참조 가능성. 구현 시 주의. |
| 11 | DANGER_LABELS에 "stairs" 없음 | COCO 80종에 stairs 없으므로 정상. 초음파로 보완. |
| 12 | Web Speech API 60초 끊김 | onend → restart 로직으로 대응 가능. |

## 3. v2 핵심 변경 요약

| 항목 | v1 | v2 | 왜 바꿨나 |
|---|---|---|---|
| **오디오 재생** | asyncio 루프 내 직접 pygame 호출 | 별도 Audio Thread + Lock | pygame이 asyncio를 블로킹하면 전체 시스템이 멈춤 |
| **LLM 호출** | 동기 블로킹 | asyncio.to_thread() + create_task() | LLM 3초 대기 중 YOLO도, WebSocket도 멈추면 시연 끊김 |
| **TTS 파일** | 임시 파일 생성 후 미삭제 | 세션 기반 캐시 + 대시보드 버튼 삭제 | 같은 말 반복 시 캐시 HIT → 즉시 재생. 디스크 관리도 해결 |
| **긴급 알림** | 항상 활성 | Stage 3에서만 활성 | 모드별로 동작이 다름. Stage 1은 대화만 해야 함 |
| **Detection loop** | FPS 제한 없음 | 30fps 제한 | CPU 100% 방지 |
| **config.py** | 검증 없음 | 필수 키 누락 시 RuntimeError | "왜 안 되지?" 디버깅 시간 절약 |
| **디렉토리 생성** | Step 0-7 (뒤쪽) | Step 0-3 (앞쪽) | 폴더 없으면 import가 안 되므로 먼저 만들어야 함 |

## 4. 스레딩 모델 도입 이유 (상세 설명)

팀원 중 비동기/스레딩이 처음인 분을 위한 설명입니다.

### 문제 상황

```
v1 코드 실행 흐름:

시간 0ms:   YOLO 감지 → 장애물 발견!
시간 10ms:  LLM API 호출 시작... (인터넷으로 요청 보냄)
시간 10ms~3000ms:  기다리는 중... (이 시간 동안 아무것도 못 함)
            → YOLO 안 돌아감 (새 장애물 못 감지)
            → WebSocket 응답 안 감 (대시보드 멈춤)
            → 다른 위험 감지 불가
시간 3000ms: LLM 응답 옴
시간 3010ms: TTS 시작... 또 기다림
```

아이가 걷는 동안 3초간 시스템이 "멈춰" 있는 것입니다.

### v2 해결

```
v2 코드 실행 흐름:

시간 0ms:   YOLO 감지 → 장애물 발견!
시간 1ms:   "LLM 호출해줘" → 별도 스레드에 위임 (즉시 복귀)
시간 2ms:   YOLO 계속 돌아감 ← 핵심!
시간 33ms:  YOLO 다음 프레임 감지
시간 66ms:  YOLO 다음 프레임 감지 (계속 돌아감)
...
시간 3000ms: (별도 스레드에서) LLM 응답 옴 → TTS → 오디오 큐에 넣기
시간 3001ms: (Audio Thread에서) 오디오 재생 시작
```

YOLO가 멈추지 않으므로 3초 기다리는 동안에도 새로운 위험을 감지할 수 있습니다.

## 5. TTS 캐시가 필요한 이유

### 같은 말을 반복하는 상황

시연 중 자주 발생하는 패턴:
- "왼쪽에 사람이 있어" (여러 번)
- "앞에 의자가 보여" (여러 번)

v1은 매번 OpenAI TTS API를 호출합니다. 호출당 0.5~1초 + 비용 발생.

v2는 처음 한 번만 생성하고 캐시합니다:

```
첫 번째: "왼쪽에 사람이 있어" → API 호출 → mp3 저장 → 재생 (1초)
두 번째: "왼쪽에 사람이 있어" → 캐시 HIT → 즉시 재생 (0ms)
```

### 왜 세션 단위로 관리하는가

캐시를 영원히 쌓아두면 디스크가 차고, 오래된 파일이 섞입니다. 시연(세션)마다 새로 시작하면:
- 깨끗한 상태에서 시작
- 대시보드 [새 세션] 버튼 하나로 초기화
- 시연 끝나면 정리 완료
